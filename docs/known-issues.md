# 既知の課題

このツールで判明している制約・未対応事項をまとめる。
**「A. 設計上の限界」は現アーキテクチャ（メインスレッド同期 CSG）では解決できず、
別アプローチでの再設計が必要。** 次期開発で対応予定。

---

## A. 設計上の限界（別アプローチでの対応が必要）

### A-1. CSG が三角形数を増やし、加工を重ねるほど破綻する 🔴
CSG（ブーリアン演算）は結果の三角形数を増やす。したがって加工を重ねるほど次の演算が
重くなり、**「1 回目は成功したのに 2 回目でタブがハングする」**という詰み方をする。
実際に `RESULT_CODE_HUNG` で作業が失われる事象が発生済み。

- **現状の緩和策:** 実行前ガード（`preflight`）／所要時間の事前警告／
  実行レポートでの三角形数の増減表示／システムプロンプトでの分割数・CSG 回数の抑制依頼。
- **根本解決:** 演算エンジンの見直し。または結果メッシュの簡略化（デシメーション）を挟む。
- **有力な候補: `three-bvh-csg` への差し替え。** A-6 の調査中に実測したところ、
  同じ形(21 個のくぼみを逐次 subtract)で **三角形 32,600 → 1,853(18 分の 1)**、
  **1,608ms → 197ms(8 倍速)**。水密性は改善しないが(A-6 の後処理で解決済み)、
  A-1 の三角形増加そのものに効く。CDN 配信可・three r160 対応。**未着手。**

### A-2. 実行中に中止できない 🔴
CSG は同期処理でメインスレッドを占有するため、開始後は中止も進捗更新もできない。
ブラウザのハング画面を JS から検知することも、「待機」を案内することも**原理的に不可能**。

- **現状の緩和策:** 開始前に確認を取る。オーバーレイに「待機を選べば続く」旨を事前表示。
- **根本解決:** **CSG の Web Worker 化。** メインスレッドが空くのでハング画面が
  出なくなり、`worker.terminate()` による中止ボタンが実現できる。

### A-3. 作業内容が保存されない 🔴
モデルはメモリ上にのみ存在する。リロード・タブ強制終了・クラッシュで全て失われる。

- **現状の緩和策:** 区切りごとの「STL 保存」を README とダイアログで案内。
- **根本解決:** IndexedDB への自動保存と復元。

### A-5. 保存した STL をスライサーで簡略化すると穴が開く 🔴(実機で発生確認済み)
A-1 と表裏の問題。CSG を重ねたモデルは三角形数が多く、Bambu Studio 等のスライサーで
「三角形が多すぎる」という警告が出ることがある。ここで**スライサー側の簡略化
(Simplify)機能で三角形を大まかに減らすと、水密性が崩れて穴が開く**。
実際に発生し、スライサー側の自動修復にかかる事象を確認済み(2026-08-17)。

**追記(2026-08-17):** スライサー側の修復機能も試したが、**必要な部分まで削られて実用にならない**
ことが判明。事後の簡略化・修復に頼る路線は断念した。

- **現状の対策:** 「増えてから減らす」のではなく**最初から作らせない**方針に変更(v0.8.0)。
  システムプロンプトの「三角形数を最小化するルール」で、CSG を使わない構成
  (`ExtrudeGeometry` + `holes` / `LatheGeometry`)を最優先させ、CSG 回数の削減
  (`mergeMeshes`)、分割数の半径連動での最小化、フィレットより面取り、を順に指示する。
  実測で三角形数は素朴な実装比 **6%(94% 削減)**(→ `architecture.md` の実測表)。
  加えて「STL 保存」時のトースト通知と info パネルでの案内(v0.7.1)。
- **残る根本解決:** 水密性を保った安全なデシメーションの組み込み、
  またはエンジンの見直し。ただし上記対策で発生頻度自体は大きく下がる見込み。

### A-6. CSG の出力が水密でない(面が欠ける) ✅ v0.9.0 で解決 / v0.9.1 で非多様体も解消
保存した STL を Bambu Studio で開くと**少しだけ面が欠けた状態**になっていた(2026-08-19 報告)。

**原因は T ジャンクションで確定(実測)。** 実物 STL(20mm ダイス, 2,240 面)を解析した結果:

- 境界エッジ(1 つの面からしか使われていない辺) **1,316 本 / 全 4,018 本 = 32.8%**
- 面のつながりで見ると **119 個のバラバラな塊**に割れていた
- 境界エッジは**すべて外側 6 面の平面上**(X=±10.2 / Y=±9.8 / Z=±10.1)に乗っていた
- 頂点溶接の精度を 1e-6 〜 1e-2 mm まで振っても境界エッジは 1,316 → 1,298 とほぼ不変
  → **「頂点が微妙にずれている」問題ではない**(`mergeVertices` では直らない)

**切り分けの結果、我々の作り方の問題ではなくライブラリの性質だった。**

| 条件 | 三角形 | 境界エッジ |
| --- | --- | --- |
| 素の `BoxGeometry` / `CylinderGeometry` / `SphereGeometry` | — | **0(水密)** |
| `CSG.subtract` **1 回**だけ(立方体 - 円柱) | 137 | **79** |
| 切削体を 0.5mm はみ出させる | 149 | 93(**むしろ増える**) |
| `CSG.union` / `CSG.intersect` | 614 / 280 | 550 / 172 |
| `three-bvh-csg` に差し替え | 106 | 70(**同様に発生**) |

→ **`three-csg-ts` は一度も水密な結果を出していない。**BSP 方式では面を平面で切るとき
「切られた面の隣の面」までは切らないため、辺の途中に他の面の頂点が乗る(T ジャンクション)。
これは BSP 系 CSG に共通の性質で、`three-bvh-csg` に替えても解決しない。

**解決策: `makeWatertight()`(v0.9.0)。**辺の上に乗っている頂点でその面を分割し直す
1 パスの後処理を、STL 保存時に掛ける。頂点は 1 つも動かさないので**形は変わらない**。

- 実測(20mm ダイス): 境界エッジ **1,316 → 0**、三角形 2,240 → 2,936(+31%)、
  体積 7767.1081 → 7767.1081 mm³(差 1.2e-5)、bbox 完全一致。
- 12 万三角形のモデルで残存 14 本 / 処理 約 4 秒。実用範囲。
- **辺上判定のしきい値は 1e-4 mm が最適。**緩めると悪化する(1e-2 mm では三角形 +336%、
  境界エッジも 4 → 59 に増加)。
- **縮退三角形(面積ゼロ)を除去してはいけない。**辺を分割した痕として位相をつないでおり、
  除去すると境界エッジが復活する(実測: 0 → 91)。コード中にコメントで明記済み。

**v0.9.1: 非多様体エッジも解消。** v0.9.0 の出力を Bambu Studio で開くと
`Error: 5 non-manifold edges` が残り、スライサー側で修復すると体積が
7767.1 → 7765.69 mm³ とわずかに減っていた(2026-08-19 報告)。解析の結果、正体は
**同じ 3 頂点で向きだけが逆の面の組 9 組** = 厚みゼロの「内部の壁」。表と裏が背中合わせに
重なった膜で、立体としての体積には一切寄与しないが、1 本の辺を 4 面以上が共有させてしまう。
**組ごと削除するのは体積保存的**なので、`makeWatertight()` の最後に除去処理を追加した。

- 実測(20mm ダイス): 境界エッジ 0 / **非多様体エッジ 17 → 0** / 体積は完全一致。
- 副次効果として**三角形の増加率が +34% → +3%** に改善(12 万〜27 万三角形で確認)。
  内部壁は分割対象としても数えられていたため。
- **溶接方式は「グリッド量子化」から変えないこと。**近傍セルまで見る「許容誤差つき溶接」も
  試したが、細い三角形を潰して境界エッジがかえって増える(12 万三角形で 14 → 432 本)。
  実物ダイスだけ見ると許容誤差つきのほうが良く見えるため、規模別の検証が必須。

### A-4. 消しゴムが 1 クリック＝フル CSG 1 回 🟡
軽い操作に見えて実際は最も重い処理を毎回走らせる。密なメッシュでは実用的でない。
A-1 の影響で、削るほど重くなる悪循環にも入る。

- **現状の緩和策:** `subtractShape()` を経由するので実行前ガードが効く。
- **根本解決:** ボクセル方式など、CSG に依らない削り方への変更。

## B. 機能上の制約（仕様として許容中）

### B-1. LLM は形状を見ていない
渡しているのはバウンディングボックスと三角形数のみ。「この出っ張りを削って」のような
部位を指し示す指示は成立しない。寸法と座標で伝える必要があり、
**3D ビューを見て判断するのはユーザーの役割**、という分担が前提。
→ 成立する指示／しない指示はチャットタブの「指示のヒント」に集約済み。

### B-2. テキスト追加は半角英数字・記号のみ
使用フォント（helvetiker）が日本語グリフを持たない。日本語対応にはフォントの
同梱・配信が必要（ファイルサイズが大きい）。

### B-3. パーツ分割はジオメトリ変更で解除される
分割結果は変更前の形状に対応するため、変更後は保持すると不整合になる。
意図的に `commitGeometry()` から `clearParts()` を呼んでいる。再分割が必要。

### B-4. undo は 12 段まで
差分ではなくジオメトリの実体をスナップショットとして保持しているため、
メモリの都合で `UNDO_MAX = 12` に制限している。

## C. 未修正の不具合・未検証項目

### C-1. `extractCode()` が最初のコードブロックだけを採用する 🟡
外部 LLM が説明用のスニペットを先に出力すると、**本命ではないコードを拾う**。
対応案: 最後のブロックを採用 / 最も長いブロックを採用 / 複数あればユーザーに選ばせる。
**未着手。**

### C-2. 実行前ガードの閾値が実測に基づいていない 🟡
`TRI_WARN = 20,000` / `TRI_CONFIRM = 60,000` は見積りの値。
実使用のフィードバックで調整が必要。

### C-3. 3MF の読み込みがブラウザ実機で未検証 🟡
`vendor/3MFLoader.js`（複数パート構成での `<component>` 参照解決の patch）は
配信されているが、実ファイルでの動作確認ができていない。

### C-4. v0.5.0 の編集機能がブラウザ実機で未検証 🟡

## D. セキュリティ（仕様として明示済み）

貼り付けたコードは `new Function` で内容を検査せずそのまま実行する。これは本質的に
任意コード実行であり、PoC としての利便性を優先した設計。
**信頼できないコードを実行しない／第三者に実行させない**ことを前提とする。
→ README・info パネルに明記済み。
